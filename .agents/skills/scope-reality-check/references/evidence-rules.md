# Evidence Rules

Use this reference only when factual verification can materially change the reality check.

## Core principle

Evidence is for deciding the verdict, not decorating it. Verify the smallest set of claims that can flip the conclusion and stop when more evidence would not change the decision.

## Evidence hierarchy

Prefer, in order:

1. Current source code, runtime state, repository files, first-party product documentation, or direct system output.
2. Official filings, statistics, standards bodies, regulators, vendor documentation, or direct announcements.
3. Reputable reporting or research with clear sourcing.
4. Community reports for experience patterns, clearly labeled as anecdotal.

Repeated social-media claims are not proof merely because they are popular.

## Freshness

Use live sources when claims depend on current pricing, limits, laws, policies, releases, repository state, outages, provider availability, or market conditions. If current verification is unavailable, downgrade precision instead of bluffing.

## Repo-specific checks

Inspect only what is needed to test the decisive claim. Useful evidence includes README promises versus actual tree contents, dependencies, entrypoints, tests/evals, CI, current branch/commit/PR state, and security-sensitive defaults.

Do not infer maturity from stars, screenshots, badges, or README polish alone.

## Reality-anchor quality

A good anchor attacks a decisive assumption. Translate vague concerns into observable failure modes.

## Precision discipline

Never invent exact numbers for rhetorical effect. Distinguish measured fact, sourced claim, inference, and scenario. Do not turn one anecdote into a universal rule or historical evidence into current state.

## Stop rule

Stop gathering evidence when the material conclusion is stable. More citations are not automatically more rigorous.
