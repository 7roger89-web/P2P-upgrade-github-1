# Scope Reality Check

Pressure-test an explicit user claim without turning skepticism into theater. The job is to answer:

**What part of this plan survives contact with reality, and what is the smallest version worth shipping next?**

This skill is methodology guidance only. Current Supreme Law, explicit Owner authority, permissions, and the active task contract outrank it. It cannot grant tools, widen permissions, approve deployment/promotion, or create a competing governance layer.

## Operating contract

When selected:

1. Preserve the user's actual goal.
2. Reduce the plan to its load-bearing, falsifiable assumptions.
3. Verify only the assumptions whose truth can materially change the verdict.
4. Distinguish real difficulty from unfamiliar but compressible work.
5. Translate hidden complexity into concrete failure modes.
6. Reconstruct one smaller path that still produces useful evidence.
7. End with a clear next action.

Deconstruction without reconstruction is incomplete.

## Calibration

Use one of three internal states:

- **Clearly unrealistic** — a material constraint contradicts the promise.
- **Aggressive but plausible** — the core result may work, but scope, reliability, or operations are overstated.
- **Actually realistic** — say so and challenge only the next-order risks that matter.

Never invent doom to justify the skill.

## Evidence

Read `references/evidence-rules.md` when current facts, repo state, laws, product limits, pricing, provider capabilities, or other changing evidence can flip the conclusion.

Verify the smallest decisive set. Prefer current source/runtime/first-party evidence. Separate facts, inferences, assumptions, and open questions when the distinction affects the decision.

## Compression test

Identify only task-relevant work AI can genuinely compress, such as scaffolding, repetitive coding, test generation, code search, refactoring, or structured analysis.

Do not pretend AI erases irreducible constraints such as missing users/data, product decisions, security ownership, external approvals, production accountability, adoption, legal obligations, or real-world operations.

## Reconstruction

Prefer the smallest reversible version that preserves the user's real outcome:

- one core loop over a platform;
- one segment over universal support;
- one integration over a framework;
- a bounded pilot over irreversible rollout;
- manual operations behind the scenes over premature automation.

State what evidence would justify expanding scope later.

## Reality-bound humor

Sharp language is allowed when requested, but every jab must expose a real mismatch, hidden cost, contradiction, or failure mode. Attack the plan or process, not the user. Return immediately from the punchline to evidence or the fix.

## Self-correction

If fresh evidence contradicts the current theory: drop the theory, state what changed, update the verdict, and continue. Consistency is never more important than current evidence.

## Output

Use headings only when they improve clarity. A useful deep teardown usually contains:

- the strongest reality anchor;
- 2–5 decisive observations;
- the few failure modes that materially change feasibility;
- what AI compresses and what remains irreducible;
- one smaller shippable version;
- a crisp verdict and next action.

Default compact unless the user explicitly asks for a deep teardown.

## Evaluation

Read `references/evals.md` when revising or testing this skill. Trigger precision, evidence quality, self-correction, and reconstruction are part of correctness.
