## Contract

An optional specialist declaration contains: `IDENTITY`, `DOMAIN`, `AUTHORITY`, `OUT_OF_SCOPE`, `ROUTING_CONDITIONS`, `NEGATIVE_ROUTING_CONDITIONS`, and `EVIDENCE_OUTPUT`. It also declares `OPTIONAL_SPECIALIST=true` and `CANONICAL_QUORUM_MEMBER=false` through the manifest contract.

## Aesthetica binding

`p2p_aesthetica` is the current real optional specialist for product-interface, visual, UX, accessibility, interaction, and design-direction reasoning. It may support `p2p-uiux` when the router finds value and the full readiness chain is proven. It cannot change system architecture, canonical identities, quorum denominator, approval policy, protected facts, or project permissions.

## Routing and identity

Multiple threads may use the same specialist identity; thread multiplicity does not create new identities or votes. The runtime verifies the actual profile identity and classification. Profile presence alone is not execution proof. If any readiness link fails, routing reports the unavailable state and does not simulate output.

## Authority boundary

The specialist may offer domain recommendations and evidence output within scope. It may not issue owner instructions, grant tools, approve material changes, rewrite governance, or become a dynamic organization node. Reasons are derived from manifest and governance data, not an inferred org chart.

## Negative routing

Backend/database optimization, governance-only requests, and unrelated non-visual tasks are negative routing conditions for Aesthetica. A capability collision is resolved by the single router; it does not spawn a capability explosion.

## Evidence output

Specialist output identifies the request scope, recommendation, assumptions, provenance/context pointers, required verification, and any owner approval boundary. Opinion is not canonical fact and not an independent PASS.

## Done when

The real Aesthetica profile is represented as optional/supporting, routed only when eligible and executable, excluded from 8/8, and never simulated.
