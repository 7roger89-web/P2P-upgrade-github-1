## Goal

Produce one Git-backed Durable Control Tower candidate that preserves the
justified durable session/packet/ledger/rotation functionality from Subject A
and the exact governance runtime binding from Subject B. The candidate must be
ready for an independent Owner Gate review, while remaining unpromoted,
undeployed, and without live runtime authority.

## Rules

- Complete P0 actual status before implementation work.
- Preserve the canonical base, Subject A worktree, Subject B worktree, and the
  historical broken Locus B root.
- Use only the existing P2P execution ledger, governance drift policy, runtime
  manifest lock, and approval boundaries.
- Treat the return packet as evidence, never as canonical truth or approval.
- Do not add a second registry, router, truth store, provider, credential path,
  adaptive council, or live host.
- Run Anvien impact/file-detail evidence before code or shared-contract edits,
  refresh Anvien before graph queries, and run detect-changes before an
  implementation commit.
- Record evidence and benchmarkable counts as they are produced.
- No canonical promotion, merge, release, deployment, credential use, or
  external communication is authorized by this plan.

## Problem

Subject A is the functional superset for the short-lived execution-session
handoff: durable session binding, exact packet parsing and fingerprinting,
existing-ledger replay, idempotency, TaskState and next-safe-task discovery,
CLI smoke coverage, attachment handoff, CT001 to CT002 rotation, recursive
continuation, and fail-closed Owner Gate boundaries. Subject A is not currently
covered by the exact runtime protected-path binding proven by Subject B.

Subject B adds the legitimate governance reconciliation, but its exact Git
history is diverged from A and it does not contain A's CLI, durable
implementation, or durable implementation test. A blind merge or wholesale
copy would therefore obscure authority and could introduce an unintended
second path.

## Scope

In scope:

- Fresh canonical identity and exact A/B Git relation evidence.
- One new candidate worktree derived from A.
- The two exact Subject B protected-path entries for
  .p2p/system/p2p_capabilities/control_tower_handoff.py.

  test and run only in the final candidate.
- Regeneration of the existing runtime-manifest lock using the existing
  governance command.

  fail-closed checks, framework comparison, change detection, and independent
  Supervisor review.
- One durable Markdown handoff containing the complete return packet.

## Non-Goals

- Repairing, initializing, replacing, copying, or deleting any .git directory.
- Modifying the broken historical Locus B root.
- Running Subject B tests in the Subject B worktree.
- P8D0A, full live council, adaptive routing, Godogen, game/PDF/voice
  runtimes, or live host certification.
- Promoting, merging, releasing, deploying, publishing, or performing live
  runtime action.
- Repairing inherited canonical baseline failures.
- Adding a new authority store, packet writer authority, router, approval
  path, provider, credential, or host-launch mechanism.

## Requirements

- Candidate relation must be recorded as DIVERGED unless fresh Git evidence
  proves another exact relation.
- Functional matrix must classify every requested surface as
  A_ONLY, B_ONLY, BOTH_EQUIVALENT, BOTH_DIFFERENT, or UNKNOWN.
- Candidate must contain A's durable source, CLI, durable tests, existing
  ledger reuse, attachment/rotation surfaces, and boundary nonclaims.
- Candidate must contain B's exact hidden-module protected entries in both
  package and installed policy paths, with no blanket whitelist.
- Candidate runtime lock must be regenerated by the existing mechanism and
  verify cleanly in package mode and the exact installed fixture mode.
- Stale-base, binding-conflict, host-isolation, attachment, rotation,
  idempotent-replay, and no-approval-inheritance behavior must remain
  fail-closed.
- Implementation SHA/tree must be sealed before evidence/report commits.
- Evidence closure SHA/tree must remain separate from the sealed implementation
  SHA/tree when reports or the handoff are committed later.
- Every terminal state must create one durable Markdown handoff, even when
  upload is not required.

## Acceptance Criteria

- Fresh canonical base SHA/tree and origin are recorded.
- Exact A/B relation and the reason for Case B minimal convergence are proven.
- Candidate contains one converged implementation with no unapproved source or
  governance mutation after implementation sealing.
- Candidate focused test suite, attachment tests, rotation tests, CLI smoke,
  compile, governance drift, doctor, and fail-closed checks have observed
  results recorded.
- Baseline comparison attributes failures to CANDIDATE_CAUSED,
  INHERITED_BASELINE, OUT_OF_SCOPE, or UNKNOWN; no inherited failure is
  silently repaired.
- Fresh independent Supervisor gives exactly PASS or REJECT for the exact
  implementation subject.
- Terminal state is one of the user-authorized values.
- Handoff is created, hashed, contains the complete return packet, and states
  that promotion/deployment/live action did not occur.
