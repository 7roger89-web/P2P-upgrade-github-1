## Purpose

Protocol for game UI/HUD design and implementation. Preserves the invariant that the game world is visually primary and the HUD serves the player's current decision horizon.

## Game UI Categories

| Category | Description | Priority |
|---|---|---|
| GAMEPLAY-CRITICAL HUD | Information essential for immediate play decisions (health, ammo, objective, minimap) | Highest |
| CONTEXTUAL HUD | Information shown only when relevant (dialog, tutorial hints, inventory on demand) | Medium |
| MENUS | Non-gameplay screens (main menu, settings, pause, shop) | Medium |
| OVERLAYS | Transient notifications (damage indicators, achievement toasts) | Low |
| DEBUG/DEV UI | Developer tools, performance overlays, console | Lowest (ship-hidden) |

## Core Invariants

1. **WORLD/GAME_VIEW = VISUALLY_PRIMARY** — The game world is the star, not the chrome around it.
2. **HUD exposes only information useful at the current decision horizon** — If the player doesn't need it now, don't show it now.
3. **DOM overlay is the default for browser HUD** — Unless spatial anchoring, rendering constraints, or XR/world-space UI is actually the product.
4. **Do not put text-heavy normal HUD inside WebGL** — Just because the game uses Three.js doesn't mean the HUD belongs in the WebGL canvas.
5. **CODE_PASS != VISUAL_PASS** — Especially for game UI where feel and readability are critical.
6. **SANDBOX_ARTIFACT != OWNER_VISIBLE_EVIDENCE** — Visual evidence must be durable and accessible from the candidate/PR.

## Avoid by Default

- Generic SaaS dashboard look on game UI.
- Oversized permanent panels covering the playable world.
- Excessive chrome (borders, gradients, shadows where they distract).
- Text-heavy canvas UI.
- Covering the playable world unnecessarily.

## Prefer

- Progressive/conditional HUD surfaces (show when needed, hide when not).
- Minimal permanent HUD (only truly gameplay-critical elements).
- Contextual surfacing (inventory opens on demand, not always visible).
- Visual hierarchy that directs attention to the game world first.
- Consistent affordances that work across input devices.

## Protocol Pipeline

```
GAMEPLAY NEEDS
  → HUD CATEGORY CLASSIFICATION
    → INFORMATION ARCHITECTURE (per category)
      → VISUAL DIRECTION (aligned with game art direction)
        → HUD LAYOUT REFERENCE
          → IMPLEMENTATION (DOM overlay by default)
            → REAL GAME RUNTIME
              → PLAYTEST / VISUAL QA
                → FIX / ITERATE
```

## HUD Implementation Decision Tree

```
Is this information needed for the player's CURRENT decision?
  NO → Hide or conditionally surface
  YES:
    Is it gameplay-critical (health, ammo, objective)?
      YES → Permanent minimal HUD element
      NO:
        Is it contextual (dialog, tutorial)?
          YES → Conditional overlay, auto-dismiss
          NO:
            Is it a menu action (inventory, settings)?
              YES → On-demand full/partial overlay
              NO → Debug/dev only (ship-hidden)
```

## DOM vs WebGL HUD Decision

| Factor | DOM HUD (Default) | WebGL/Spatial HUD |
|---|---|---|
| Text readability | ✓ Excellent | ✗ Poor for small text |
| Layout flexibility | ✓ CSS Flexbox/Grid | ✗ Manual positioning |
| Accessibility | ✓ Native browser a11y | ✗ Custom implementation |
| Performance | ✓ Minimal overhead | ⚠ Canvas rendering cost |
| Spatial anchoring | ✗ Not possible | ✓ World-space |
| XR/VR requirement | ✗ Not possible | ✓ Required |
| Visual consistency with 3D | ⚠ Limited | ✓ Full integration |

**Decision**: Use DOM HUD unless one of the right-column factors is a genuine product requirement.

## Playtest / Visual QA

1. Run the actual game with HUD visible.
2. Record gameplay with HUD in context.
3. Evaluate: Does the HUD distract from the game world?
4. Evaluate: Is gameplay-critical information immediately readable?
5. Evaluate: Do conditional surfaces appear/disappear appropriately?
6. Compare against reference HUD layouts.
7. Fix and re-verify.

## Done When

- HUD categories classified.
- Information architecture defined per category.
- Visual direction aligned with game art direction.
- HUD implemented (DOM or WebGL as justified).
- Real game runtime visual QA completed.
- Playtest evidence preserved in durable location.
