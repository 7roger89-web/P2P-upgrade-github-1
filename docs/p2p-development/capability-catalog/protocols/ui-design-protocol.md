# P2P UI Design Protocol

## Purpose

Compact reusable protocol for UI/UX design workflows across P2P projects. Preserves the invariant that visual direction must precede blind component assembly.

## Protocol Pipeline

```
USER/JOB REQUIREMENTS
  → INFORMATION ARCHITECTURE
    → VISUAL DIRECTION
      → REFERENCE / IMAGEGEN
        → DESIGN TOKENS / SYSTEM
          → COMPONENT STATES
            → IMPLEMENTATION
              → REAL BROWSER / RUNTIME
                → RESPONSIVE / VISUAL QA
```

## Required Semantics

### USER/JOB REQUIREMENTS
- Identify the user (beginner, power user, operator, player).
- Identify the job-to-be-done (not just the feature name).
- Identify success criteria (what does "done" look like to the user?).

### INFORMATION ARCHITECTURE
- Map the information hierarchy (what is primary, secondary, tertiary).
- Identify navigation patterns (tab bar, sidebar, breadcrumbs, none).
- Identify empty/loading/error/success states upfront.

### VISUAL DIRECTION
- Establish visual direction BEFORE selecting any component library.
- Visual direction is project-specific, not library-imposed.
- Reference images, mood boards, or imagegen outputs anchor direction.
- **Invariant: COMPONENT_FOUNDATION != VISUAL_DIRECTION**

### REFERENCE / IMAGEGEN
- Use reference images or imagegen to concretize visual direction.
- Lock references before implementation begins.
- **Invariant: SANDBOX_ARTIFACT != OWNER_VISIBLE_EVIDENCE**

### DESIGN TOKENS / SYSTEM
- Extract tokens: color palette, typography scale, spacing scale, border radii, shadows.
- A component library (e.g., shadcn-ui) supplies primitives that consume tokens.
- Tokens encode project identity; libraries encode mechanical affordance.

### COMPONENT STATES
- Enumerate states: idle, hover, focus, active, disabled, loading, error, empty, success.
- Mobile/touch states where applicable.
- Accessibility states (focus ring, aria attributes).

### IMPLEMENTATION
- Implement components consuming tokens and state definitions.
- Component library is a primitive source, not a visual identity.

### REAL BROWSER / RUNTIME
- **Invariant: CODE_PASS != VISUAL_PASS**
- Code correctness does not prove visual correctness.
- Open the actual runtime (browser, device, game view) for human review.

### RESPONSIVE / VISUAL QA
- Test across breakpoints (mobile, tablet, desktop).
- Test across themes (light/dark if applicable).
- Compare implementation screenshots against reference images.
- Fix deviations and re-verify.

## Surface Evaluation Criteria

For important surfaces, evaluate:

1. **Hierarchy** - Is the primary action/information immediately visible?
2. **Typography** - Are font sizes, weights, and line heights appropriate?
3. **Spacing** - Is whitespace consistent with the design token system?
4. **State Coverage** - Are all states implemented and tested?
5. **Affordance** - Are interactive elements obviously interactive?
6. **Responsive Behavior** - Does the layout adapt gracefully?
7. **Accessibility** - Are keyboard navigation, focus management, and ARIA attributes correct?
8. **Empty/Loading/Error/Success** - Are all lifecycle states handled?
9. **Mobile/Touch** - Are touch targets adequate? Is content readable on small screens?

## Anti-Patterns

- Starting implementation before visual direction is established.
- Treating a component library as a design system (it supplies primitives).
- Forcing a generic dashboard look on non-dashboard products.
- Skipping the real-browser check.
- Assuming CODE_PASS implies VISUAL_PASS.

## Done When

The project has:
- Locked visual direction reference.
- Design tokens defined.
- Component states enumerated.
- Real browser/runtime visual QA completed.
- Responsive QA completed.
- Screenshot evidence preserved in durable location.
