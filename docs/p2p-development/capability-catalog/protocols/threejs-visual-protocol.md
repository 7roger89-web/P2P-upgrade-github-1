## Purpose

Protocol for Three.js/R3F visual production, quality assurance, and capability orthogonality. Preserves the separation of visual, spatial, navigation, performance, cinematic, and authoring concerns.

## Capability Orthogonality

These capabilities are **orthogonal** — each serves a distinct concern and must not be conflated:

| Capability | Concern |
|---|---|
| `game.three.visual` | Rendering, materials, lighting, post-processing, visual style |
| `game.three.asset` | Model loading, texture management, animation clips, asset pipeline |
| `game.three.cinematic` | Camera animation, cutscenes, timeline-driven motion |
| `game.three.spatial_query` | Raycasting, BVH, collision detection, spatial indexing |
| `game.three.navigation` | Navmesh, pathfinding, NPC movement |
| `game.three.adaptive_quality` | GPU detection, quality tiers, dynamic resolution, LOD |
| `game.three.scene_authoring` | Scene editors, prefab systems, visual scene building |

**Do not install all of them just because PROJECT_PROFILE=THREEJS_GAME.** Route by actual need.

## Visual QA Pipeline

```
VISUAL DIRECTION
  → REFERENCE IMAGE(S)
    → SCENE / ASSET IMPLEMENTATION
      → ACTUAL RUNTIME
        → SCREENSHOT CAPTURE
          → REFERENCE COMPARISON
            → CORRECTION
              → PERFORMANCE / RESPONSIVE QA
```

### Stage Details

**VISUAL DIRECTION**
- Define the target visual style (realistic, stylized, toon, pixel-art 3D, etc.).
- Lock direction before implementation.
- Visual direction is authoritative over any capability's default aesthetic.

**REFERENCE IMAGE(S)**
- Use concept art, mood boards, or imagegen output.
- Lock references before scene implementation.
- **Invariant: SANDBOX_ARTIFACT != OWNER_VISIBLE_EVIDENCE**

**SCENE / ASSET IMPLEMENTATION**
- Build the scene using Three.js/R3F primitives and activated capabilities.
- Each capability activated only when its concern is needed.
- Do not activate `game.three.spatial_query` for a scene that only needs visual rendering.

**ACTUAL RUNTIME**
- Open the real browser/runtime.
- **Invariant: CODE_PASS != VISUAL_PASS**
- Code correctness does not prove visual correctness.

**SCREENSHOT CAPTURE**
- Capture screenshots from the actual runtime.
- Use consistent camera angles and lighting for comparison.

**REFERENCE COMPARISON**
- Compare implementation screenshots against reference images.
- Identify deviations in color, lighting, composition, material quality.

**CORRECTION**
- Fix identified deviations.
- Re-capture and re-compare.

**PERFORMANCE / RESPONSIVE QA**
- Measure frame rate, draw calls, texture memory.
- Test across device tiers (if adaptive quality is activated).
- Test across viewport sizes.
- Verify that performance optimizations don't regress visual quality below the locked direction.

## Adaptive Quality Caveats

When using `game.three.adaptive_quality` (e.g., detect-gpu):

1. **GPU_TIER = HEURISTIC** — The tier is a best-effort classification, not authoritative device capability.
2. **GPU_TIER != AUTHORITATIVE_DEVICE_CAPABILITY** — A tier-3 GPU may still struggle with specific workloads.
3. **Stale Data Risk** — Benchmark data sources may stop updating (e.g., gfxbench.com stopped December 2025).
4. **Conservative Fallback** — Always provide a safe default for unknown GPUs.
5. **Never unlock critical gameplay functionality based on benchmark match alone** — Use adaptive runtime measurement in combination.

## Capability Activation Checklist

Before activating each capability, verify:

| Capability | Activation Question |
|---|---|
| `game.three.visual` | Does the project need custom materials, lighting, or post-processing? |
| `game.three.asset` | Does the project load 3D models, textures, or animation clips? |
| `game.three.cinematic` | Does the project need camera animation, cutscenes, or timeline-driven motion? |
| `game.three.spatial_query` | Does the project need raycasting, collision detection, or spatial indexing? |
| `game.three.navigation` | Does the project need navmesh or NPC pathfinding? |
| `game.three.adaptive_quality` | Does the project need device-tier-based quality adjustment? |
| `game.three.scene_authoring` | Does the project need a scene editor, prefab system, or visual scene builder? |

If the answer is **NO**, do not activate the capability.

## Anti-Patterns

- Activating all Three.js capabilities because the project uses Three.js.
- Treating `game.three.visual` as synonymous with `game.three.spatial_query`.
- Using GPU tier as the sole determinant of gameplay feature availability.
- Skipping the real-runtime visual check.
- Allowing a capability's default aesthetic to override project visual direction.
- Installing R3F-only capabilities in a vanilla Three.js project.

## Done When

- Visual direction locked.
- Reference images locked.
- Only needed capabilities activated (with justification recorded).
- Real runtime visual QA completed.
- Performance/responsive QA completed.
- Screenshot evidence preserved in durable location.
