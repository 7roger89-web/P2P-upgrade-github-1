## Deliverable C — Execution Backend Feasibility Decision

### Verdict: `HERMES_BACKEND_PROMISING` (qualified)

Evidence-based reasoning. **A. Can P2P call Hermes without modifying P2P core for Hermes-specific behavior?** Yes for the headless contract surface: `cli.py -p` (oneshot) and event-stream-driven sessions provide structured input, structured JSON events, exit status, session identity, workspace binding (cwd), permission configuration (approval policy), model/provider selection (config), SIGINT cancellation, and `IterationBudget`-bounded execution (max_iterations default 500, per-subagent default 50). The adapter boundary is precisely the C30 ExecutionTarget composition (Harness=hermes, Provider/Model from P2P registry, Protocol, ToolSet, Workspace) plus the P2P execution contract envelope. Hermes-specific behavior never enters P2P core — it is encapsulated in the harness profile and adapter. Caveats: event format is Hermes-native and must be normalized by the adapter; Hermes's transcript-based durable state must be ignored in favor of P2P's own state (adapter extracts verifiable artifacts only).

**B. Minimal adapter** (design only, not implemented): `HermesExecutionBackendAdapter` implementing the C30 execution contract with ~six responsibilities: (1) translate P2P execution contract → Hermes CLI invocation (`cli.py -p "<goal>" --session <id> --workspace <path> --config <adapter-config>`); (2) stream-parsing of the monitoring event JSONL into normalized P2P evidence events; (3) exit-status → contract-result mapping; (4) cancellation forwarding (SIGINT) + ESTOP-style pause sentinel per run; (5) budget enforcement at the adapter layer (`max_iterations` injection) independent of Hermes defaults; (6) artifact harvesting (tool results, modified files, exit code) for P2P verification, with transcript kept as optional evidence-of-execution, never as state. Estimated surface: one harness profile record + one adapter module; no core change.

**C. C30 fields Hermes can provide directly:** Harness identity (binary + version via `codex`-equivalent `hermes --version` style call), provider/model identity (config), protocol (openai-completion-compatible transport), toolset surface (enumerable from Hermes tool registry — adapter enumerates, never routes), workspace identity (bound cwd), permission profile (approval policy), health probe (process liveness; `hermes doctor`-equivalent), exit status, structured events. Fingerprint input is fully derivable → `fingerprint()` works on Hermes targets today.

**D. Fields an adapter must derive:** Capability evidence per ToolSet (adapter enumerates tool names + permission levels; honest UNKNOWN for unstated capabilities), auth-state evidence (adapter must invoke P2P's own C31 auth-state model, not Hermes's credential handling — this keeps the C31 blocker honest: Hermes inherits OPENAI_API_KEY semantics), certification/health ladder (adapter converts liveness + auth-state + freshness into the health ladder), evidence freshness (timestamped adapter observations), contract-drift detection (adapter re-enumerates tools/versions and compares fingerprints).

**E. Would Hermes reduce maintained execution machinery?** Materially yes, for the harness layer: terminal execution, tool registry, shell profiles, context management/compression, memory, skills loading, browser tools, cancellation, interruption, observability, token accounting — all come with the harness. What P2P still must own is everything the ledger marks `P2P_SHOULD_OWN`: durable state, eligibility, fingerprint/drift, certification, governance gates, continue/owner-gate policy, budgets, verification, evidence integrity. Net: P2P keeps the control plane fully and delegates the engine. Estimate: removes the majority of "engine" build effort for a first backend while keeping every governance surface P2P-owned.

**F. New dependency/lock-in risks:** (1) Vendor surface growth — Hermes is a fast-moving product (daily commits, v0.20.2 as of 2026-08-16); CLI contract can drift, so the adapter must pin versions and re-certify via fingerprint/drift gates (already in C30 machinery). (2) Implicit routing temptation — `relay_llm.py`/`relay_runtime.py` demonstrate automatic provider fallback; the adapter must never enable it (REGISTRY != ROUTER). (3) Transcript-as-state habit — Hermes's session-dir persistence is seductive; P2P must enforce state ≠ transcript at the verification layer. (4) Safety-optionality — `--dangerously-skip-permissions` shows harness safety can be defeated by a single flag; P2P governance gates must be enforced by the adapter/control plane, not assumed from the harness. (5) License: MIT — permissible, but P2P C32 deliberately copies no code (pattern-level adoption only), so license risk is negligible. (6) Cost/availability of the harness itself (npm/Python install, network to provider APIs) — covered by INELIGIBLE_AUTH freshness gates.
