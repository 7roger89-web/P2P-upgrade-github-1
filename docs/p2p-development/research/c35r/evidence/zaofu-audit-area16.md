# ZaoFu Audit Findings: Observability, Dashboard, CLI, API, Deployment & Maturity

## CLI Surface (`src/zf/cli/*.py`)
The ZaoFu CLI provides a comprehensive interface for managing the harness, implemented using `argparse` with numerous subcommands. The `zf` command is defined in `src/zf/cli/main.py` and registers over 40 subcommands covering various aspects of the system, including project and profile management (`profile`, `init`, `config`, `project`, `workspace`, `backlog`), execution and workflow control (`start`, `stop`, `restart`, `attach`, `run`, `workflow`, `flow`, `autoresearch`, `autopilot`), observability and status (`status`, `events`, `trace`, `kanban`, `logs`, `metrics`, `cost`, `panes`, `projection`, `goal`), recovery and repair (`recover`, `self_repair`, `doctor`, `check`), and integrations (`feishu`, `bridge`, `channel`, `agent`). The CLI is designed to be a thin layer over the core logic, heavily relying on `zf.core` modules. For example, `zf profile bootstrap` uses `zf.core.profile.apply` and `zf.core.profile.detector` to detect the project stack and materialize configuration in `zf.yaml`. The CLI commands depend on `zf.core` modules and `zf.integrations`. The CLI is well-structured, extensively documented in `docs/manual/03-cli-operations.md` and `docs/manual/09-zaofu-cli-usage.md`, and supported by tests such as `tests/test_workflow_audit_cli.py`.

## Web Dashboard & API (`src/zf/web/*`, `web/`)
ZaoFu provides a local web dashboard for observability and interaction. The backend, implemented in `src/zf/web/server.py`, is a FastAPI server that exposes endpoints like `/api/state` (Kanban, features, cost, workers snapshot), `/api/views/tasks`, `/api/views/workers`, `/api/stream` (SSE for events), `/api/cost`, and `/api/progress`, and also serves the static frontend assets. The frontend, located in the `web/` directory, contains a React/Vite application using TypeScript and Playwright for testing. The backend is designed to be stateless and read fresh data on every request, reading directly from `kanban.json` and `events.jsonl` to avoid cache invalidation bugs. The API provides projections of the system state, such as the Agent View worker/session cockpit projection and Kanban projection. The web backend depends on `zf.core.state`, `zf.core.cost`, and `zf.runtime`, while the frontend consumes the API endpoints. The web dashboard is marked as "F-WEB-MVP-01: thin local Web dashboard" and is an optional dependency installed via `pip install -e ".[web]"`. It is supported by tests like `tests/test_web_server.py` and `tests/test_web_overview_pulse.py`.

## Operator Dashboards & Session Observability
Observability is deeply integrated into ZaoFu. Modules like `src/zf/web/overview_pulse.py` and `src/zf/web/headless_turn_observability.py` provide specific observability features, while CLI commands such as `trace`, `events`, `kanban`, `logs`, `metrics`, and `cost` allow CLI-based observability. The system tracks events in an append-only log (`events.jsonl`). The web dashboard provides a "Kanban + features + cost + workers snapshot" and SSE streaming of events. Observability depends on the event system (`zf.core.events`) and state management (`zf.core.state`).

## Deployment & Install Complexity
Deployment is handled via standard Python packaging using `pyproject.toml`, with the entry point defined as `zf = "zf.cli:main"`. The base install requires `PyYAML>=6.0` and Python `>=3.11`. Optional dependencies include `dev` (pytest, ruff, etc.), `stream-json`, `web` (fastapi, uvicorn, websockets), and `feishu` (lark-oapi). The project relies on standard Python tooling like uv/pip. The `README.md` provides clear installation instructions, such as `uv sync --extra dev --extra web --extra stream-json`.

## Windows Compatibility
The codebase acknowledges Windows environments, particularly in command parsing and virtual environment handling. `src/zf/core/self_eval/contract.py` contains specific logic for Windows, including `_WINDOWS_EXECUTABLE_SUFFIXES` and `_WINDOWS_PROVIDER_EXECUTABLE_RE`. Additionally, `src/zf/runtime/candidates.py` checks `os.name == "nt"` to determine the virtual environment bin directory (`.venv\Scripts` vs `.venv\bin`). Windows compatibility appears to be partially implemented, focusing on critical path elements. Documentation does not explicitly mention Windows support.

## Background Autonomy & Daemon Processes
The system uses background threads for various tasks rather than heavy daemonization like systemd services for local execution. `src/zf/cli/feishu_consume.py` runs the inbound-reply-stream-card chain in a background thread, and `src/zf/runtime/channel_message_ingress.py` has `dispatch_channel_replies_background`. `src/zf/web/headless_agent.py` uses daemon threads for reading stdout and stderr. Background processing is well-integrated, particularly for I/O-bound tasks and third-party integrations, relying on Python's `threading` and `concurrent.futures` modules.

## Test/Eval Coverage & Maturity/Stability Signals
The `tests/` directory is extensive, containing 968 Python files and 1547 total files. Key test files include `test_web_server.py` (145KB), `test_workflow_graph_runtime.py` (38KB), `test_writer_fanout_runtime.py` (322KB), and `test_workdirs.py` (44KB). The test suite covers core workflows, web server, artifact management, feishu integration, and more. Pytest is configured in `pyproject.toml` with coverage enabled. The high number of test files and the presence of large, detailed test files indicate a strong focus on stability and extensive test coverage. The project is at version `0.0.5`, suggesting it is still in an active development/preview phase despite the extensive codebase.
