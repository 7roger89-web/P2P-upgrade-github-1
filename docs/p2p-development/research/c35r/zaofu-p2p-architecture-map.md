# P2P–ZaoFu Architecture Map (C35R)

**Goal:** C35R — ZaoFu Deep Architecture Audit (research only)
**Scope:** Subsystem-by-subsystem mapping of [uisee-ai/zaofu](https://github.com/uisee-ai/zaofu) ("An open-source Coding Harness Platform for long-horizon, multi-agent software delivery", Apache-2.0, v0.0.5, main `@ b5e569dd45a9743ddfa82cf08e8d3f4b8a4bdcd3`, retrieved 2026-08-18) against P2P at `c35-provider-neutral-runtime @ 7c9cb58`.
**Style:** Pointer-based evidence only. Full evidence for each area lives in `evidence/zaofu-audit-areaNN.md`. No large upstream source copies.

## A. Governance planes — where the two systems do NOT overlap

| Plane | ZaoFu | P2P | Overlap | Stronger for P2P's goal |
|---|---|---|---|---|
| Canonical role governance | None: agents are spawned sessions with `channel_roles` and provider-specific skill materialization (`skills/materialize.py` → `.claude/skills/`, `codex-home/skills`); no equivalent of P2P's 8 canonical roles | 8 canonical roles + aesthetica, `RoleExecutionContract`, `role_eligibility` fail-closed, `role_verifier`, 8/8 quorum (`role_quorum.py`) | ~0% | **P2P** — this is the authority P2P must never surrender |
| Owner Gates / human-in-the-loop | Mix-in control actions (`control_actions_plan.py` etc.): agent recommends, operator clicks; actor fixed to `operator` | Owner Gates (C10, C14 `OWNER_APPROVAL` DONE), approval policy | Partial (both have operator veto) | **P2P** — owner-level gates are first-class governance, not a CLI surface |
| Quorum / independent verification of claims | No concept of multi-claim quorum; verification gates are AND-closure within one judge flow | `expected_task_id=ALL`, UNKNOWN vs INCOMPLETE, deterministic verifier | ~0% | **P2P** |
| Evidence / provenance of frozen artifacts | `Attestation` over 6 frozen classes (task contract freeze, State Packet, dispatch manifest, role-instructions briefing, skills manifest, research index); schema "1.0" (`core/security/attestation.py`) | `identity_hash` SHA-256 on canonical JSON; receipt evidence pointers; candidate `package_verify_evidence` | Partial (both hash-based, different scopes) | Comparable; ZaoFu's attestation scope is broader for *dispatch* artifacts, P2P's is broader for *capability/candidate* lineage |
| Promotion / release governance | `candidate_*.py` (candidate idempotency, incremental/integration lineage) exists but no analog of P2P's UNPROMOTED→PROMOTED→VERIFIED lanes | Candidate records, `CANDIDATE_REQUIRED` policy lane, lineage | ~0% | **P2P** |

**Reading:** ZaoFu is an *execution harness*; P2P is a *governance + runtime system*. The authority plane (who may do what, who verifies, who promotes) belongs to P2P in every area above.

## B. Execution & orchestration planes — where ZaoFu is materially richer

| Subsystem | ZaoFu approach | P2P current approach | Material difference | Stronger for P2P's goal |
|---|---|---|---|---|
| Deterministic kernel | 4 pure I/O-free state machines (`TaskStateMachine`, `WorkerStateMachine`, `SessionStateMachine`, `LoopStateMachine`); `EventActionRegistry` with YAML-declared actions; `ControlledActionOrchestrator` for replayable actions | Role-level determinism via `RoleExecutionContract` + receipt state machine; C33 bounded-retry observer; C18 adaptive policy | ZaoFu has a full *task/worker/session/loop* lifecycle + explicit `recovering` state; P2P has role-level determinism only | **ZaoFu** for lifecycle depth; **P2P** for claim-level trust |
| State authority | CAS-style `authority_revision = SHA256({task_id, sequence, contract, execution_binding})` → `authority-r<hash>`; phase *derived* from `events.jsonl` via `derive_phase()`; `kanban.json` is a projection | `identity_hash` SHA-256 over canonical capabilities/contract JSON; quorum receipts as authority; goal-closure CONSISTENT gate | ZaoFu's CAS revision chain is explicit and versioned; P2P's quorum-of-receipts model is more trust-oriented | **ZaoFu** for state revisioning; **P2P** for trust semantics |
| Task contract | Rich dataclass: behavior + verification + `verification_tiers` (static/runtime/e2e/manual_evidence) + scope + owner_role/instance + source precedence refs + `execution_profile_id`/digest + per-task quality-gate overrides + claim ids | Dict-based `CONTRACT_SCHEMA` (schema, allowed_scope, verify_spec, forbidden_actions); C34 `verify_spec`; C35 `RoleExecutionContract` 22 fields | ZaoFu packs behavior, verification tiers and provenance into one contract object | **ZaoFu** as a contract *shape*; P2P keeps contract responsibilities split across C33–C35 layers on purpose |
| Execution harness | `BackendAdapter` + `BackendCapabilities` matrix (hooks/resume/usage-reader/stream-json/nested-agent/child-lineage…); `ClaudeCodeAdapter` + `CodexAdapter` (deep, provider-specific CLI flags); `BackendSessionReader` → normalized `UsageReport` | C20/C30 `ExecutionTarget` composition + fingerprint/drift; C34 `BackendAdapterIdentity` + `BackendExecutionBridge`; `BackendCapabilityCertification` LIVE_CERTIFIED_FOR_CAPABILITY | ZaoFu's matrix is declarative and avoids `if backend ==` branches; P2P's certification is claim-based and auditable per capability | **ZaoFu** for capability-declaration ergonomics; **P2P** for certification authority |
| Event log & persistence | Append-only `events.jsonl` (+ index + dedupe `BoundedIdSet`); SQLite `read_model.sqlite` as *rebuildable projection* ("never replace the append-only log as business truth"); git state snapshot | Receipt/event append, candidate manifest, governance JSON projections; no event-sourced read model | ZaoFu has a mature event-sourcing read-model pattern | **ZaoFu** for observability projection; P2P's governance projections are simpler and auditable |
| Recovery / bounded retry | `LoopStateMachine` failed→recovering; `RecoverySeries` per task+contract revision; `rework_dispatch_count` enforces cap; `build_rework_cap_payload` injects retry bounds into events; `valid_series_failures` ignores replay/stale; quarantine → bug candidate on cap exhaustion (`quarantine_candidate_from_plan`); rework evidence extracted from real stdout/stderr | C33 bounded-retry observer (AutoPilot); no cap-aware quarantine, no failure-evidence rework messages, no `recovering` lifecycle state | ZaoFu's recovery is end-to-end: cap, evidence, quarantine, replay-safe counting | **ZaoFu** — a clear gap P2P can adapt |
| Verification | `gates.py` (CommandGate/FileExistsGate) → `Evidence` → `JudgeEvaluator` (correctness/completeness/quality/coverage, grade A–D); multi-discriminator AND-closure; `completion_honesty.py` anti-hallucination; goal-closure bridge binds `required_reads` and pinned claim sets to the Thin Judge; `GoalClosureResult` schema | `role_verifier.py` fail-closed failure classes; evidence pointers in receipts; deterministic quorum gate; C35 goal-closure machine `CONSISTENT` | ZaoFu's Thin Judge is a *read-only role at closure boundary* with required-read contracts; P2P's verifier is role-level and fully deterministic | **ZaoFu** for the closure-judge *pattern*; **P2P** for deterministic verification |
| Context delivery | `context_delivery.py`: immutable source manifest → sectioned context (`required`/`delta_allowed`) → delivery envelope bound to workflow/task/contract/session/permission identity; `write_context_delivery_receipt` records delivery without claiming reads; `task_context_manifest.py` four-facet manifest (implement/check/research/closeout) with `missing_required_refs` + `read_receipt_gaps`; `briefing_hydration` | C19 task-targeted context DONE; C36 (Context/Cache/Token/Cost intelligence) planned; no delivery-envelope or read-receipt accounting yet | ZaoFu models "what the agent should read" as a durable manifest with per-section digests and delivery receipts | **ZaoFu** — directly reusable for C36 |
| Adaptive execution | YAML-declared `workflow.event_actions` → `EventActionRegistry` handlers; reactor; `control_actions_*` mixins (plan, proposal, recovery, replay, resume, run); budget gating (`check_budget` → halt) | C18 adaptive orchestration policy DONE (policy foundation); C37 (adaptive target/model/effort selection) planned | ZaoFu's action-declaration plane is concrete and operator-visible | **ZaoFu** as a design reference for C37 control-plane actions |
| Multi-agent / fanout | `channel_router` (mention gates), `channel_discussion` state machine (idle→blind→relay→synthesis→idle) with quorum/deadlines; `autoresearch` 31 files (orchestrator, triggers, failure signals 67KB, review gates); writer fanout + join; autoscaled worker instances with git worktrees | C17 bounded parallel execution DONE; role fanout via canonical roles; no discussion state machine, no autoresearch supervisor | ZaoFu has a full supervisory self-repair loop and channel-based deliberation | **ZaoFu** for the fanout/deliberation layer; out of scope for P2P's C35 lane |
| Cost / budget | `cost/tracker.py` (cost.jsonl active+archive), `BillingAdapter` (OpenAI/Anthropic), `PricingCatalog`/`RateResolution`, `check_budget`; `briefing_metrics` soft budgets; `automation_metrics` (autonomy/reliability/governance-drift signals) | Usage evidence in `BackendExecutionResult`/receipts; C36 cost intelligence planned | ZaoFu has live budget enforcement; P2P records evidence but no enforced budget | **ZaoFu** pattern relevant to C36 |
| Security / side-effects | `PathGuard.assert_disjoint` + `.zf-workdir-owner.json`; `NonceManager`; `EventSigner`; SHA-256 attestations kernel-owned (workers cannot mutate); permission bypass flags documented (`--dangerously-skip-permissions`) | C10/C14 owner approval; C28 credential onboarding; permission-envelope invariant `permission-envelope-never-widens` (architectural_invariants) | Different layers: ZaoFu filesystem-path safety vs P2P permission-governance | **P2P** on governance authority; ZaoFu useful filesystem-safety ideas |
| Observability | CLI 40+ subcommands; FastAPI local dashboard (Kanban+cost+workers, SSE stream); stateless reads from `kanban.json`/`events.jsonl`; `doctor`/`self_repair` | Beginner routing, evals, reports; no live dashboard; `p2p_goal_closure` + `p2p_beginner_certification` machinery | ZaoFu is operator-dashboard oriented; P2P is certification-machine oriented | Different goals; not an overlap problem |
| Windows / portability | Partial (`_WINDOWS_EXECUTABLE_SUFFIXES`, `os.name == "nt"` venv paths); undocumented | P2P beginner-first targets broad environments; capsule/installer lifecycle DONE | ZaoFu is macOS/Linux-first | P2P |

## C. Verdicts summary (detail in `zaofu-build-vs-reuse-matrix.json`)

| # | Question | Answer |
|---|---|---|
| 1 | Is P2P rebuilding ZaoFu? | **Partial overlap in the execution layer only** — P2P's C35 runtime (role spec/contract/receipt/quorum) occupies the trust layer ZaoFu never addresses. P2P is not rebuilding the harness (workspace isolation, provider CLI spawning, streaming). |
| 2 | Is ZaoFu rebuilding part of P2P? | **No.** ZaoFu has no canonical role governance, no quorum-of-receipts, no Owner Gates, no promotion lanes, no beginner-first certification machinery. |
| 3 | Can ZaoFu become a P2P ExecutionTarget / harness backend? | **Conceptually yes** — its `BackendAdapter`/`BackendCapabilities` seam is precisely what an ExecutionTarget wants, and C27 evidence shows Codex CLI is already installable. But it is not needed: P2P's C34/C35 seam already spawns providers natively. |
| 4 | Should P2P depend directly on ZaoFu? | **No.** v0.0.5, ~2 weeks old, no stable release policy, Apache-2.0 (compatible) but deep Codex coupling; dependency would violate P2P's `p2p-is-sole-orchestrator` invariant. |
| 5 | Should P2P vendor or fork ZaoFu? | **No** — research decision: audited, non-vendored (same posture as Semantica research). |
| 6 | Should P2P copy any ZaoFu modules? | **Selective adapt only**: recovery mechanics (rework cap, quarantine), Thin-Judge pattern (read-only closure judge with required reads), context-delivery envelope + read receipts. |
| 7 | Which concepts adapt first? | Bounded retry/rework cap with evidence-based rework messages; `BackendCapabilities`-style capability matrix; briefing/context packaging with delivery receipts. |
| 8 | What can P2P stop building? | Anything in the raw-execution layer already solved upstream — P2P never planned to build it anyway, so the practical stop list is short; the audit confirms P2P should stay out of that layer entirely. |
| 9 | What must P2P keep owning? | All 13+ governance-boundary items: goal truth, task identity, canonical roles, role authority, permissions, Owner Gates, evidence/provenance, independent verification, quorum, durable project truth, provider-neutral contracts, eligibility, recovery governance, promotion/release governance, beginner-first UX. |
| 10 | Does C35 architecture remain correct? | **Yes.** The audit found nothing that invalidates the provider-neutral agent runtime; the receipt/quorum model and ZaoFu's CAS/event model are complementary. |
| 11 | Should C36 change? | **MINOR_REFINEMENT** — adopt ZaoFu's context-manifest + delivery-envelope + read-receipt concepts into the planned context/cost layer. |
| 12 | Should C37 change? | **MINOR_REFINEMENT** — adopt the declarative capability-matrix + control-action (operator-visible verbs) concepts; no redesign. |

## D. Confidence and caveats

The audit inspected implementation at one HEAD (`b5e569dd`). ZaoFu is very young (v0.0.5, 2 weeks old); some subsystems (e.g., Claude Code adapter, Windows support) are documented as less mature than Codex. Provider neutrality of ZaoFu's *core* is genuine, but its *integration layer* is Codex-deep. All overlap percentages and decisions in the matrix are judgment-based estimates supported by pointer evidence in `evidence/`; they are research inputs, not committed design.
